# 08 AI 协作工作流

本文约束「人如何向 AI 提需求、AI 如何在本仓库工作」。机器可执行版见根目录 [AGENTS.md](../../AGENTS.md) 与 `.trae/rules/`。

## 1. 基本原则

1. **AI 不是所有者**：它只能在既有架构内实现需求，不得自创架构、目录、依赖。
2. **最小改动**：能改 1 个文件就不改 3 个；能复用就不新建。
3. **先读后写**：未读取相关代码与规则前，AI 不得产出修改。
4. **可验证**：每次交付必须给出验证命令与结果。
5. **有疑必问**：需求歧义、破坏性变更、新增依赖必须先确认。

## 2. 标准任务流程

```text
需求 → 定位（读规则 + 读代码） → 对齐（有歧义则提问）
     → 计划（列出改动文件） → 最小实现
     → 自检（npm run check） → 汇报（改了什么/影响/风险）
```

AI 在以下情况**必须暂停并询问**：

- 需要新增依赖
- 需要修改公共模块导出、路由结构、构建/lint 配置
- 需求与现有规范冲突
- 影响范围超过 3 个业务域
- 发现既有 bug 但与当前任务无关（记录，不擅自修）

## 3. 好的任务描述（Prompt 模板）

```markdown
## 目标
在用户列表页增加「按状态筛选」，状态值来自 order-status.constant.js。

## 范围
只改 src/views/user/UserListView.vue 与 src/api/user.js；不要动其他页面。

## 约束
- 遵循 AGENTS.md 与 .trae/rules
- 不新增依赖
- 三态齐全，筛选变化时保留分页

## 验收
- [ ] 切换状态后请求参数正确
- [ ] 空数据显示空态
- [ ] npm run check 通过
```

关键点：**明确边界**（改哪些、不改哪些）、**明确验收**（怎么算完成）。

## 4. AI 禁止行为（与红线对应）

| 行为 | 原因 |
| --- | --- |
| 为过检查改 lint/构建配置 | 掩盖问题，破坏门禁 |
| 加 `eslint-disable` / `@ts-ignore` / `@ts-nocheck` | 规则形同虚设 |
| 在 JS 中写 TS 类型语法 | 项目不引入 TypeScript |
| 直接删改「看起来没用」的代码 | 可能被动态引用 |
| 重构无关模块 | 扩大回归面 |
| 自造目录/命名/工具函数 | 破坏一致性 |
| 用 Pinia 传父子状态 | 增加隐式耦合 |
| 组件内直接发请求 | 绕过统一错误处理 |
| 硬编码颜色与魔法数字 | 破坏主题与一致性 |
| 提交 `console.log` / 注释代码 | 污染仓库 |
| 声称"已完成"但未跑检查 | 交付不实 |

## 5. 交付说明格式

```markdown
## 改动
- src/views/user/UserListView.vue：新增状态筛选与三态展示
- src/api/user.js：fetchUserList 增加 status 参数

## 原因
需求「用户列表按状态筛选」，原接口已支持 status 字段。

## 影响
仅用户列表页；其他调用 fetchUserList 的位置未传 status，行为不变。

## 验证
- npm run check：通过
- 手动：切换状态 → 请求带 status → 空态正常

## 风险
无。若后续列表需要缓存筛选条件，可提升到 query 参数。
```

## 6. 人工评审 AI 产出的重点

- [ ] 是否引入新依赖、新目录、新抽象
- [ ] 是否有 `eslint-disable` / `@ts-ignore` / TS 语法混入
- [ ] 是否只改了该改的文件
- [ ] 三态与异常分支是否真实存在（不是写的假代码）
- [ ] 是否复用了既有组件与工具
- [ ] JSDoc 是否与实现一致
- [ ] 检查是否真的执行过

## 7. 规则维护

- 每次 AI 犯错，先判断是「规则缺失」还是「规则未被遵守」：
  - 缺失 → 补 `docs/standards` + `.trae/rules`；
  - 未遵守 → 检查规则是否可被自动检测，能自动化就写进 ESLint/Stylelint。
- 规则总数保持精简，宁可少而硬，不要多而软。
